# V40 — Top-level field-aware model merges

`previewObjectMerge()` and `mergeObjectRevisions()` now support **automatic
three-way synthesis** of independent top-level field edits for the 18 canonical
hydraulic entity kinds represented by `HydraulicObjectKind<T>`.

The existing V37/V39 API remains source-compatible. There is no SQLite
migration and no change to previously finalized revision hashes.

## Merge behavior

An entity changed differently on both branches was formerly always a
`Conflict`. For supported typed entities with a valid common-ancestor payload,
matching kind and UUID, V40 compares **each serialized top-level Model field**:

- If both sides make the same change, keep that value once.
- If only the left side changes a field, keep the left value.
- If only the right side changes a field, keep the right value.
- If both sides change the same field differently, add its name to
  `ObjectMergeChange::conflicting_fields` and retain `Conflict`.
- If all fields are resolvable, report `ObjectMergeKind::FieldsMerged` and
  provide a fully encoded `automatically_merged` object. The commit operation
  automatically applies it in the existing atomic, validated write transaction.
  **No** explicit resolution is permitted for a `FieldsMerged` object.

The same canonical `QDataStream` encoder used by `ModelCodec` compares fields
**byte-exactly**. No floating-point tolerance, implicit unit conversion,
ordering heuristic, or UUID remapping is applied. Model payload UUIDs are
checked against the object key before attempting a field merge. A configure-time
schema check ensures the 18 typed merge handlers explicitly cover every field
listed in the pinned codec schema.

## Conservative boundaries

In V40, nested structs (such as `metadata` or `coordinate_wgs84`) and lists
(such as junction demands or pipe vertices) were **atomic fields**. V42 adds
independent subfield handling specifically for `EntityMetadata`; all other
nested structs and collections remain atomic.

Deletion versus modification, type changes, simultaneous incompatible creation,
legacy arbitrary/invalid bytes, unsupported object kinds, and inputs larger
than 4 MiB per object remain subject to the previous entity-level behavior.
The new `conflicting_fields` list is empty for unsupported payloads: that does
**not** imply the conflict is automatically resolvable.

V40 required whole-entity conflict choices. V41 added per-field resolutions;
V42 extended those to `metadata.*` subfields.

## Safety and tests

The merged bytes are generated by decoding and encoding the pinned canonical
Model type and are never constructed by raw stream splicing. All existing
permission, generation, physical-object digest, edit history, structural
validation, transaction rollback and cryptographic finalization checks remain
in the V39 commit path. Structural validation does **not** run EPANET.

`aowis-db-object-merge-fields` exercises a two-field synthesis, overlapping
field names, nested metadata (extended in V42), an opaque entity fallback, an edited local
working revision, and late SQL failure rollback. No test-only hashing shortcut
or build-script behavior change is introduced.
